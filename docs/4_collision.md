# 4. 충돌 처리와 IK — 기초 · 현재 구조 · 문제 · 개선 계획

> Phase 2 를 제대로 돌리려면 **"로봇을 그 자세로 보낼 수 있는가"** 와
> **"가는 길에 뭘 안 치는가"** 두 가지가 맞아야 한다. 이 문서는 그 두 가지를
> 기초부터 정리하고, 지금 코드가 어디까지 하고 있는지, 무엇을 고쳐야 하는지 적는다.

## 0. 왜 Phase 2 부터 어려운가

| | Phase 1 | Phase 2 (NBV) |
|---|---|---|
| 로봇 자세 | **한 번** 잡고 고정 | 부족한 면마다 **새 자세로 이동** |
| 턴테이블 | 한 바퀴 회전 | 한 바퀴 회전 |
| 필요한 것 | 좋은 자세 1개 | 자세를 **계속 새로 풀고**, **이동 경로가 안전**해야 함 |

Phase 1 은 좋은 자리 하나만 찾으면 끝난다. 로봇이 안 움직이므로 충돌 위험도 거의 없다.
Phase 2 는 "빈 곳을 보러 가는" 단계라 **매번 IK 를 풀고 매번 경로를 검사**해야 한다.
그래서 IK 와 충돌이 부실하면 Phase 2 부터 티가 난다.

## 1. 기초 — 용어 네 개

### 1.1 FK 와 IK

- **FK(정기구학)** : 관절각 → 손끝 위치. "각 관절을 이만큼 돌리면 손이 어디 가지?"
  계산이 **한 번에 딱** 나온다. 답이 하나다.
- **IK(역기구학)** : 원하는 손끝 위치 → 관절각. "손을 여기 두려면 관절을 어떻게 돌리지?"
  **답이 여러 개거나 없다.** 이게 모든 어려움의 출발점이다.

xArm7 은 관절이 7개인데 자세를 정하는 데 필요한 건 6개(위치 3 + 방향 3)다.
남는 1개를 **여유자유도**라 하고, 덕분에 **같은 손끝 자세를 만드는 관절조합이 무한히**
많다. 팔꿈치를 위로 들든 옆으로 빼든 손끝은 같은 곳에 둘 수 있는 것과 같다.

### 1.2 시드(seed) — 왜 "못 푼다"가 거짓말일 수 있나

우리가 쓰는 IK 는 **수치해법(DLS)** 이다. 공식으로 딱 푸는 게 아니라,
**어떤 관절각에서 출발해 조금씩 고쳐가며** 목표에 가까워지는 방식이다.
이 출발점을 **시드**라 한다.

```
시드 A 에서 출발 → 목표 도달 O
시드 B 에서 출발 → 엉뚱한 데서 갇힘 → "도달 불가" 라고 보고 X
```

**같은 목표인데 시드에 따라 성공/실패가 갈린다.** 시드를 하나만 쓰면
실제로는 갈 수 있는 자세를 "못 간다"고 버리게 된다.
실측: 수직 파지가 시드 1개면 0/8, 12개면 8/8.

### 1.3 roll — 공짜로 얻는 자유도 하나

카메라가 물체를 바라볼 때, **광축(보는 방향) 둘레로 카메라를 돌려도 같은 면을 본다.**
사진을 찍고 나서 회전시킨 것과 같다. 3D 스캐너도 마찬가지다.

그런데 코드에서 흔히 쓰는 `look_at(eye, target, up=(0,0,1))` 은
"위쪽은 하늘 방향" 이라고 **roll 을 하나로 못 박는다.** 그러면 공짜 자유도를 버리는 것이다.

실측: 같은 위치에서 roll 을 고정하면 el 30° 자세가 0/8, 풀면 5/8.
**시드를 12개로 늘려도 roll 을 고정하면 여전히 0/8** 이었다 → 시드로 대체 안 된다.

### 1.4 충돌 검사 — 도형으로 근사한다

메시(삼각형 수십만 개)끼리 직접 거리를 재면 느리다. 그래서 보통 **단순 도형으로 감싼다.**

- **캡슐** = 선분 + 반경 (알약 모양). 링크 하나를 원기둥처럼 덮는다. 빠르다.
- 문제: **관절 원점을 잇는 직선**이라, 실제로 꺾여 있는 링크를 덮으면 **실제보다 뚱뚱해진다.**

```
실제 링크 :  ┌──┐
             │  └──┐        ← 꺾여 있음
캡슐 근사 :  ●━━━━━━━●      ← 직선으로 덮음 → 빈 공간까지 "링크"로 침범
```

그 결과 **안 부딪히는데 부딪힌다고 판정**한다(오탐). 실측: 캡슐 축간 58mm 로 "충돌"인데
실제 메시 거리는 93mm 였다.

## 2. 지금 IK 는 어떻게 푸는가

### 2.1 솔버는 이미 통일돼 있다 ✅

**sim 과 real 이 같은 solver 를 쓴다** — `utils/robot/xarm7_kinematics.ik` (자체 해석 DLS).

```
sim  : isaac_scan_session._view_q          → kin.ik(pose6d, seed)
real : artec_multipass_scan_session._axis_view_q → _kin.ik(pose6d, seed=q_seed)
       xarm_interface.ik                   → _kin.ik(...)
```

`utils/robot/ik_provider.py` 에 결정 근거가 남아 있다:

> ★ 결정(2026-06): xArm SDK IK 미사용. SDK IK(`get_inverse_kinematics`)는 **컨트롤러 통신**이라
> 하드웨어 연결 필요 → 불안정. 그래서 real·sim 모두 오프라인·안정한 자체 해석 IK 를 쓴다.

**이 결정은 옳다.** 계획 단계(오프라인)에서 수백 개 후보 자세를 검사해야 하는데,
SDK IK 는 로봇에 연결돼 있어야 하고 왕복 통신이라 느리다. 유지 권장.

잔여물 하나: `utils/control/hardware_layer.py:303` 이 도달성 확인용으로
`arm.get_inverse_kinematics` 를 아직 부른다. 계획 경로가 아니라 확인용이지만,
**같은 질문에 두 솔버가 다른 답을 낼 수 있으므로** 해석 IK 로 통일하는 게 맞다.

### 2.2 진짜 차이는 solver 가 아니라 **그 주변** ⚠

같은 solver 를 쓰지만 **어떻게 부르느냐가 다르다.** 안전 문제는 여기서 생긴다.

| 항목 | sim (`_view_q`) | real (`_axis_view_q`) |
|---|---|---|
| roll | **6방향 시도**(0,∓45,∓90,180) | **고정 1개** |
| IK 시드 | **8개**(주어진 것 + 대안 7) | **1개** |
| 카메라 규약 | `look_at_camera` (**USD, −Z 광축**) | `compute_camera_pose_from_normal` (**OpenCV, +Z**) |
| 자가충돌 | **실제 메시** | 캡슐 |

세 번째가 특히 중요하다 — **같은 (el, az) 를 줘도 두 경로가 서로 다른 카메라 방향을
만든다.** 규약이 다르면 부호가 뒤집히거나 축이 바뀐다.
지금은 각자 자기 hand-eye(`T_EC`)와 짝이 맞아 동작하지만, **sim 에서 검증한 자세가
real 에서 같은 자세라는 보장이 없다.** 시뮬레이션으로 실물을 검증한다는 전제가 깨진다.

## 3. 지금 충돌은 어떻게 보는가

### 3.1 자가충돌(로봇이 자기 몸을 침) — 실제 메시 ✅

`utils/collision/mesh_self_collision.py` (2026-08 신규)

```
링크 메시를 링크 로컬 좌표로 샘플링 → KD-tree 를 한 번만 구축
자세마다 툴 점을 각 링크 로컬로 역변환해 질의 (트리 재구축 없음 → 자세당 수 ms)
프레임은 해석 FK. USD 대비 위치 1.5~8.6mm / 회전 1.4° 로 일치 확인
```

| 검사 쌍 | 이유 |
|---|---|
| 툴 ↔ link1~5 | link6/7 은 툴이 붙은 인접 링크라 항상 닿아 있음 → 제외 |
| link6 ↔ link1~3 | 손목 뭉치가 몸통에 접근 |

임계 20mm (`MMS_SIM_SELF_CLEAR`). 캐시 `utils/collision/data/xarm7_spider_links.npz`

| # | 문제 | 위험 |
|---|---|---|
| **P1** | **셀 구조물이 장애물에 없다** — 벽·상판(Z=0.510)·저울·툴스탠드 전부 미등록 | el=30 처럼 낮은 자세는 팔이 아래로 뻗는다. **실물에서 상판을 칠 수 있다** |

## 5. 개선 계획 — **P1·P3·P4 완료 (2026-08-18)**

### 5-1. 셀 구조물을 장애물로 등록 ✅ (P1)

`utils/collision/env_collision.py` + `scripts/sim/export_env_mesh.py` (신규)

```
셀 메시 129개 → 88,190점을 **로봇 base 프레임**으로 구워 npz 캐시
KD-tree 1회 구축 → 자세마다 link3~7 + 툴 점을 질의 (수 ms)
여유 25mm (MMS_SIM_ENV_CLEAR).  link1/2 는 천장 마운트에 상시 근접 → 제외
```

base 프레임 저장이 핵심 — **sim·real 공용**이고, 실물은 같은 CAD 를 같은 방식으로
구우면 그대로 쓴다. `mesh_self_collision` 과 대칭 구조.

동작 확인(자세별 최소거리가 실제로 변한다):

```
home                  207.3mm     관절2 +70°       58.4mm
관절2 +40°(아래로)      27.3mm     전부 0(수직)    225.7mm
```

### 5-2. 장애물 검사도 메시로 ✅ (P2, 5-1 과 함께 해결)

캡슐 world(turntable/tt_frame/keepout)는 **그대로 두고** 메시 검사를 **추가**했다.
캡슐은 과대평가(안전 방향)라 제거할 이유가 없고, 미탐만 메우면 된다.
`_pose_collision_reason` 순서: 캡슐 scene → **메시 env** → 메시 self.

### 5-3. `_view_q` 공용 모듈 승격 ✅ (P3, P4)

`utils/robot/view_pose.py` (신규) — sim·real 이 같은 함수를 부른다.

| | 이전 sim | 이전 real | 지금 |
|---|---|---|---|
| roll | 6방향 | 1개 | 공용 6방향 |
| IK 시드 | 8개 | 1개 | 공용 8개 |
| 규약 | USD | OpenCV | **인자로 전달**(각자 유지) |

**규약 통일이 안전했던 이유** — 두 규약은 카메라 로컬 Y축 **180° 회전 하나**만 다르다:

```
R_usd^T · R_cv = diag(-1, 1, -1)      전 (el,az) 동일, 편차 1.8e-12
카메라 원점은 완전히 일치
```

따라서 규약을 **데이터(convention 인자)** 로만 넘기면 되고, `T_EC`(hand-eye)는
각 경로가 자기 것을 그대로 쓴다 → **캘리브레이션 무변경**.

회귀 검증:
- 공용 모듈의 OpenCV 출력 = real 기존 `compute_camera_pose_from_normal` (오차 1e-12)
- roll=0·시드1 로 제한 시 real 기존 IK 결과와 **9/9 완전 일치**
  → real 은 기존에 풀리던 자세의 해가 그대로, 안 풀리던 것만 추가로 열린다

### 5-4. `hardware_layer` 도달성 확인을 해석 IK 로 (P5) — 미완

`utils/control/hardware_layer.py:303` 의 `arm.get_inverse_kinematics` → `kin.ik`.
계획 경로가 아니라 확인용이라 위험도는 낮다.

### 검증 방법

각 단계마다 **대조군을 두고 A/B** 로 확인한다(env 스위치).
"고쳤더니 좋아졌다"를 한 번의 실행으로 판단하지 않는다 —
이 프로젝트의 boundary 지표는 실행마다 867~918mm 로 흔들린다.

## 6. 로봇팔 충돌 회피 — 일반적인 방법

> Phase 에 상관없이 **하나의 게이트**로 막아야 한다. 지금은 Phase 2 만 검사하고
> Phase 1·3 은 무검사다(§3 참고). 아래는 업계에서 널리 쓰는 선택지 정리.

### 6.1 무엇으로 검사하나 — 형상 표현

| 표현 | 속도 | 정확도 | 비고 |
|---|---|---|---|
| 구·캡슐·박스 (primitive) | ★★★ | ▲ 과대 | 지금 장애물에 사용. 꺾인 링크에 부적합(§5) |
| **볼록 분해** (V-HACD 등) | ★★ | ★★ | 산업 표준. GJK/EPA 로 거리·침투 계산 |
| 메시 BVH/KD-tree | ★ | ★★★ | 지금 자가·셀에 사용. 자세당 수 ms |
| **SDF·복셀** (Octomap 등) | ★★★ | ★★ | **환경에 최적** — 한 번 굽고 O(1) 조회. 로봇은 점으로 질의 |

실무 조합: **로봇 = 볼록 분해(또는 잘 맞춘 캡슐), 환경 = SDF/복셀**.
로봇은 링크 수가 적어 정밀 표현이 싸고, 환경은 크지만 정적이라 미리 구울 수 있다.

### 6.2 언제 검사하나 — 이산 vs 연속

- **이산(pose check)** — 자세 하나만. 시작·끝이 안전해도 중간은 모른다.
- **이산 보간(discretized swept)** — 지금 방식(12스텝). **터널링** 위험이 있다:
  스텝 간격이 얇은 장애물보다 크면 그냥 통과해 버린다.
  → 보완: **적응적 스텝** — 관절 최대 이동량 × 링크 길이가 여유보다 작도록 스텝 수 결정.
- **연속(CCD, conservative advancement)** — 관통 불가를 보장. FCL·Bullet 지원.

### 6.3 어떻게 피하나 — 계획 수준

| 방식 | 설명 | 대표 |
|---|---|---|
| **검사 후 거부** | 후보를 검사해 통과한 것만 사용 | **지금 방식** |
| 샘플링 기반 계획 | 막히면 **우회 경로**를 탐색 | RRT-Connect, PRM (OMPL/MoveIt) |
| 최적화 기반 | 충돌 비용 gradient 로 경로를 밀어냄 | CHOMP, STOMP, TrajOpt, **cuRobo** |
| 반응형 | 실행 중 실시간 회피 | potential field, CBF, velocity damping |

지금은 "거부"뿐이라 **우회가 없다** — 직선 보간이 막히면 그 자세를 포기한다.
Phase 2 가 "feasible 없음"으로 끝나는 원인 중 일부가 이것이다.

### 6.4 자가충돌 특화 — ACM

인접 링크는 **항상** 닿아 있으므로 무시 목록이 필요하다. MoveIt 은 이를
**ACM(Allowed Collision Matrix)** / SRDF 로 **데이터로** 관리한다.
지금은 코드에 하드코딩돼 있다(`TOOL_VS_LINKS`, `LINK6_VS_LINKS` in
`utils/collision/mesh_self_collision.py`) → 링크 구성이 바뀌면 코드를 고쳐야 한다.

### 6.5 라이브러리

| 이름 | 특징 | 이 프로젝트 적합성 |
|---|---|---|
| **FCL / HPP-FCL** | 표준. primitive+mesh+CCD, 거리 질의 | ◎ 경량, ROS 불필요 |
| **cuRobo** (NVIDIA) | GPU 가속 모션생성 + 충돌, Isaac Sim 연동 | ○ sim 엔 최적, real 은 GPU 필요 |
| Bullet / PhysX | 물리엔진 씬 쿼리. Isaac 에 이미 있음 | △ sim 전용 |
| MoveIt | ACM+계획+검사 통합 | △ ROS 의존 |
| Pinocchio + hpp-fcl | 경량 운동학+충돌 | ◎ real 경로에 무난 |

### 6.6 이 프로젝트의 제약과 권장

**제약**: real 은 Isaac 없이 돌아야 한다 → 순수 numpy 또는 경량 라이브러리만 가능.
그래서 PhysX·cuRobo 를 real 판정에 직접 쓸 수 없다(sim 검증용으로는 유효).

**단기 (구조 변경 없이)**
1. **단일 게이트로 통합** — `is_pose_safe(q)` / `is_path_safe(q0,q1)` 하나를 만들어
   Phase 1·2·3 이 모두 그것만 부르게 한다. 지금은 Phase 2 만 검사한다.
2. **적응적 스텝** — 고정 12스텝 대신 관절 이동량 기반으로 결정(터널링 방지).
3. **ACM 을 데이터로** — 무시 링크쌍을 yaml 로 빼고 sim·real 공유.

**중기**
4. 환경을 **SDF/복셀**로 (지금 KD-tree 88k점 질의 → O(1) 조회).
5. 막혔을 때 **우회 경로**(RRT-Connect 등). "거부"만으로는 Phase 2 가 자주 막힌다.


## 7. 구현 결과 (2026-08-18~19)

§6 의 권장을 실제로 구현했다. **의존성 추가 없음**(numpy/scipy만) — hpp-fcl·pinocchio 는
`env_isaacsim` 에만 있고 실물 환경(`mms-env`)에는 없어, 쓰면 sim/real 격차가 되살아난다.

### 7.1 단일 게이트 — `utils/collision/collision_model.py`

```
로봇  = 링크 로컬 메시 점군 (해석 FK 로 배치)
환경  = SDF 거리장 8mm       ← O(1) 조회
자가  = 링크 로컬 SDF 6mm     ← 이게 20배 속도의 원천
```

`clearance` → `is_pose_safe` → `is_path_safe` 3층. **Phase 무관** — 모든 이동이
`_drive`(sim) / `_move_robot_to_q`(real) 를 지나므로 여기 한 곳에 넣으면 1·2·3 이 모두 덮인다.

**자가충돌도 SDF 로 바꾼 것이 핵심.** 프로파일링: 114.5ms 중 **111ms 가 자가충돌 KD-tree**
질의였고 환경 SDF 는 36k점에 6.6ms 였다. 같은 방식을 자가에 적용해 **5.75ms/자세**(20배).

격자 밖 조회는 `pad` 를 돌려준다 — 격자가 bbox+pad 를 덮으므로 밖의 점은 최소 pad 만큼
떨어져 있다는 **참인 하한**이다. 거짓 '안전'을 만들지 않는다.

### 7.2 보수적 전진 — 적응적 스텝보다 근본적

> 자세 q 의 여유가 s 이고 구간에서 어떤 점도 s 보다 멀리 움직이지 않으면,
> 그 구간은 **중간 검사 없이 안전이 보증**된다.

```
                  검사 횟수    시간
동일 자세            2회      11.6ms
관절1 5°             2회      10.6ms
home→0 대이동        35회     243.8ms   (고정 123스텝은 707ms)
```

빠르면서 **터널링이 원리적으로 불가능**하다. 고정/적응 샘플링은 둘 다 샘플 사이를 못 본다.

### 7.3 우회 — `utils/control/joint_path_planner.py` (RRT-Connect)

직선이 되면 즉시 반환(대부분), 막히면 양방향 RRT 로 우회 + shortcut 평활화.

실측: 안전 자세 12개 중 **직선이 막힌 쌍이 6개**, 시험한 3개 모두 우회 성공(1.3~2.3s,
전 구간 재검증 통과). **"막히면 포기"가 실제로 자세를 절반 가까이 잃고 있었다.**

### 7.4 ⚠ 표면 샘플링 — 정점만 담으면 **부재가 텅 빈다**

가장 위험했던 버그. 스캐너가 `/World/frame/HFS8_4040_1000_04`(4040 프로파일 1m 기둥)를
**관통**했다. 원인:

```
부재 정점 1,694개가 전부 **양 끝단**에 몰려 있고 중간 1m 에는 0개
   → 점군 SDF 는 점이 있는 곳만 장애물로 본다 → 중간이 텅 빈 복도
```

CAD 압출·판재는 정점이 모서리에만 있다. `GetPointsAttr()` 만 담으면 안 된다.
→ `utils/collision/mesh_sampling.py` 로 **삼각형 면적 비례 표면 샘플링**.

```
             전체 점       기둥 중간(0.3~0.7Z)
이전         88,190              0점    ← 관통
현재      1,301,122          6,963점    Z 전 구간 균일
```

점이 15배 늘어도 **판정 속도는 그대로**다(SDF 는 격자 조회라 점 수와 무관).

교훈 — **검증도 틀렸었다.** "SDF 가 부재를 본다(3.3mm)"고 보고했는데, 부재 **자신의 정점**으로
질의해 끝단만 확인한 것이었다. 표면 전체를 훑었어야 했다.

### 7.5 특이점 회피 — 관절각 규칙이 아니라 σ_min

`xarm7_kinematics` 에 `singular_values` / `manipulability` / `sigma_min` 추가.
**단위 정규화 필수** — `_numeric_jacobian` 은 위치 행이 mm/rad 라 그대로 SVD 하면
위치가 1000배 커서 회전 특이점이 묻힌다. 위치를 m 로, 회전에 특성길이 0.3m 를 곱한다.

실측 분포(무작위 1500자세): 최소 0.0004 / 1% 0.0020 / 5% 0.0076 / 중앙 0.069
→ **임계 σ_min ≥ 0.05** (하위 ~4% 절단, home 0.147 로 3배 여유)

**7축은 6축의 손목 특이점(q5=0)이 특이점이 아니다** — 실측 σ_min 0.16. 남는 축이 보상한다.
실제로 나쁜 것은 팔꿈치가 상한으로 펴진 q4≈157° 형상이며, **자코비안을 봐야만** 나온다.
→ 관절각 규칙은 이 팔에서 틀린 답을 낸다.

적용은 두 곳: `view_pose.solve_view_q`(조건 나쁜 해를 버리고 **다음 후보 탐색**) +
`CollisionModel.is_pose_safe`(자세·경로·우회 전부 자동 적용).

### 7.6 턴테이블이 방위각을 담당한다 — 충돌을 **구조적으로** 줄이는 원칙

로봇이 az 를 만들려고 물체 주위를 돌면 팔이 크게 감싸 위험해진다. 실측
(물체중심 겨냥, standoff 0.313m):

| az | 관절이동 | 자가여유 | 환경여유 | 판정 |
|---|---|---|---|---|
| **0°** | **58°** | **52mm** | **217mm** | OK |
| 30° | 95° | 60mm | 137mm | OK |
| −30° | 362° | 12mm | 0mm | 충돌 |
| −60° | 409° | **3mm** | 18mm | 충돌 |
| −90° | 445° | **1mm** | 112mm | 충돌 |
| 180° | 345° | 68mm | 0mm | 충돌 |

**16개 조합 중 9개가 충돌 기각**되고, az 를 벌릴수록 관절이동이 8배 늘고 여유가 1mm 까지
떨어진다. 그런데 **방위 커버리지는 전회전이 이미 제공**하므로 로봇이 az 를 만들 이유가 없다.

→ `VIEW_AZIS_DEG` 를 `[0, 30, -30]` 으로 축소(`MMS_SIM_VIEW_AZIS`).
**턴테이블 = 방위각, 로봇 = 고도각·거리**가 이 셀의 기본 원칙이다.

### 7.7 메모리 안전 — PC 를 멈춘 뒤 넣은 장치

표면 샘플링에 상한이 없어 OOM 으로 **작업 PC 가 멈췄다**(EXIT=137). 세 겹으로 막았다:

1. `per_tri_cap` / `max_pts` / float32 — 극단 입력(10m² @1mm = 1억점)이 8,196점으로 차단됨
2. 삼각분할 **완전 벡터화** — 파이썬 루프가 직접 원인이었다(23만 삼각형 0.03초)
3. `/tmp/runguard.sh <RSS_GB> <명령...>` — 초과 시 프로세스만 죽여 PC 를 지킨다
   (`ulimit -v` 는 CUDA 가상주소 예약을 깨뜨리므로 Isaac 에 쓰지 말 것)
