```

턴테이블 축         (0.365, 0)             ← base 바로 아래
바닥(캐스터 하단)    Z = -0.071            상판 universal_plate 상면  Z = 0.510
```

v2 에서 v3 로 넘어오며 base 가 ΔX −173mm, ΔZ +93mm 움직였다. **Z 보다 X 이동의 영향이
훨씬 크다** — v3 는 base 가 턴테이블 축 바로 위에 와서 낮은 고도각이 기구학적으로
빡빡해졌다(§3).

## 2. 관측 자세 지정 규약

```python
eye = target + standoff * (cos(el)·cos(az), cos(el)·sin(az), sin(el))
standoff = WORK_FOCUS(0.25) + 물체반경
```

표면이 Spider 스윗스팟(작동거리 0.2~0.3m)에 오도록 물체 반경을 더한다. **az 는 커버리지
기여가 거의 없다** — 턴테이블이 방위각을 담당하므로, az 는 "그 자세에 팔이 닿는가"를
찾는 용도로만 스윕한다(`collision.md` §5).

**el 다양성이 중요한 이유** — Spider 는 FOV 가 좁고(~30°) 작동거리가 짧아 한 자세가 덮는
면적이 작다. 낮은 el 이 없으면 옆면과 아랫부분이, 높은 el 이 없으면 윗면이 안 찍힌다.

## 3. 배치 결정 — 턴테이블을 옮길 필요가 없다

셀이 만족해야 할 것은 셋이었다. ① 스캔 거리가 스윗스팟(0.2~0.3m)일 것, ② 관측 el 이
30~80° 로 다양할 것, ③ F* 그리퍼로 턴테이블 위 물체를 집을 수 있을 것.

한동안 **낮은 고도각이 전부 막히는 것을 레이아웃 한계로 보고 턴테이블 이설을 검토**했다.
그런데 roll 자유도를 풀자 현재 위치에서 셋 다 성립했다.

```
el=30  5/8      파지 el=90(수직)  8/8      IK 위치오차  최대 0.39mm / 평균 0.16mm
el=40  7/8      파지 el=75        8/8      표면까지 거리 25.0cm (스윗스팟 중앙)
el=50  7/8      파지 el=60        8/8
el=60  8/8      파지 el=45        8/8      스캔 IK 실패 0건
el=70  8/8                                 (남은 6건은 자가충돌 2 · 환경 4)
el=80  7/8
```

파이프라인 실측이 결론을 확인해 준다.

| | 이설 전(v3) | 턴테이블 이설(v4) | roll 수정 후(v3 그대로) |
|---|---|---|---|
| preview | 0점 | — | 5,502점 |
| lookaround 자세 | el 50~70 | — | el 30 |
| 누적 점군 | 15,019점 | 38,844점 | **50,839점** |

**하드웨어를 옮긴 쪽보다 옮기지 않고 코드를 고친 쪽이 나았다.** 이후 메시 자가충돌과
NBV 정렬까지 고치자 172,869점까지 올라갔다(boundary 867→853mm 단조 감소).

### 프레임 20cm 상승은 유지한다

세 번의 독립 실행에서 부호가 일관됐다.

| base Z | 스캔 | 피킹 |
|---|---|---|
| 1.500 (v3) | 399~422 | 258 |
| 1.407 (v2) | 362~391 | 223~226 |
|  | +8~10% | +14~16% |

팔이 천장에 매달린 구조라 **높을수록 아래쪽 작업공간이 넓어진다.** 최적 X 에서의 차이는
더 커서 피킹이 22 대 13 이다.

### 확정 사항

- 턴테이블 이설 불필요 — 현재 X=0.365 에서 el 30~80, 수직 파지, 거리 25cm 모두 성립
- 프레임 20cm 상승 유지
- 저울 간섭 문제 소멸(옮기지 않으므로 철판 설계도 불필요)

## 4. roll 을 푼 것에 대하여

낮은 고도각을 연 것은 시드가 아니라 **roll** 이다.

| 조건 (X=0.365) | el 30 | el 40 |
|---|---|---|
| roll 고정 + 시드 1개 | 0/8 | 0/8 |
| roll 고정 + 시드 12개 | 0/8 | 0/8 |
| **roll 자유** + 시드 12개 | **5/8** | **7/8** |

시드는 파지에만 기여했다. 재현: `eval_turntable_layout.py --diag 0.365 --rolls 0`(대조군)
대 `--diag 0.365`.

**실물 tracking 관점에서 roll 을 풀어도 되는 근거**는 둘이다. 패스 내부에서는 로봇이 q 를
유지하고 턴테이블만 돌므로 **roll 이 상수**라 프레임 간 정합과 무관하다. 패스 사이에는
어차피 위치·자세가 모두 바뀌고, roll 은 그 점프의 한 성분일 뿐이며 relocalization 이 이미
그걸 처리하도록 설계돼 있다.

안전장치로 `VIEW_ROLLS_DEG` 는 **크기 순(0, ∓45, ∓90, 180)** 이라 roll=0 해가 있으면 그대로
쓰고 없을 때만 최소 각도로 넓힌다. 실물에서 tracking-lost 가 늘면 `MMS_SIM_VIEW_ROLLS=0`
으로 즉시 되돌린다.

부수효과 — FOV 가 비등방(hfov 30° / vfov 22.62°)이라 roll 은 0.25m 에서 발자국을
134×100mm ↔ 100×134mm 로 회전시킨다. 유효성이 아니라 커버리지 형태의 문제다.

# 〔부록〕 Troubleshooting

### T1. 캡슐 기반 초기 스윕 결과는 폐기됐다
`sweep_turntable_x.py` 의 X 스윕 점수는 캡슐 오탐이 섞인 값이라 쓰지 않는다. 캡슐이 꺾인
링크를 직선으로 덮어 빈 공간까지 충돌로 판정한다(`collision.md` T4). 배치 판단은 메시
판정으로 다시 낸 §3 의 수치를 쓴다.

### T2. 〔한계〕 물체 크기 상한
측면 가장자리가 축에서 30.7cm 면 스윗스팟 상한이다. **반경 63mm 를 넘는 물체는 standoff
재계산이 필요**하다. 지금은 `WORK_FOCUS + r` 로 자동 계산되지만 상한을 넘는지 확인하지
않는다.

### T3. 〔미지원〕 sim 에 flip 가 없다
`supports_flip()` 가 sim 에서 False 다("물체 손회전 불가"). 설계상 의도지만, sim 은
물체가 USD prim 이라 프로그램으로 뒤집을 수 있다. 구현하면 실물 투입 전에 3단계 전체를
검증할 수 있다.

주의할 점 둘 — 뒤집은 뒤 누적은 flip 변환의 역을 적용해 canonical 프레임으로 되돌려야
하고, 대상이 강체이므로 물리 pose 도 함께 갱신해야 한다.

### T4. 〔미해결〕 남은 gap 은 관측으로 못 메운다
남은 gap 의 법선 고도각 중앙값이 **−12~−13°** 다. 수평보다 아래에서 올려다봐야 하는 면
(물체 하단이 말린 부분)이라 el ≥ 30 으로는 원리적으로 불가능하다. **flip 이 유일한
해법이다.** 아랫면(n_z < −0.6)으로 분류되는 것은 0~2개뿐이고 대부분 '측면'으로 잡히지만
실제로는 살짝 아래를 향한다.

### T5. 〔미해결〕 커버리지 지표와 gap 수가 안 맞는다
`cov` 가 0.97~1.00 인데 gap 18 이 유지되는 경우가 있다. 각도 커버리지 판정과 gap 검출의
기준이 어긋나는지 확인이 필요하다. 종료 판정은 지금 gap 회계가 내므로 당장 문제가 되지는
않는다(`4_nbv.md` §6).
