# 하드웨어 레이아웃 — 규약 · 실측 · 배치 실험

턴테이블 위치를 정하기 위한 문서. **로봇 base 고정, 턴테이블 위치가 설계변수.**

만족해야 할 것
1. 스캔 거리가 스윗스팟 (Artec Spider 작동거리 **0.2~0.3m**)
2. 관측 elevation 이 **30~80°** 로 다양하게 나올 것
3. F* 그리퍼(3F Delto)로 턴테이블 위 사물을 **집을 수 있을 것**

---

## 1. 각도 규약 — el / az / standoff

관측 자세는 대상 주위 **구면 좌표**로 지정한다.

```python
eye = target + standoff * (cos(el)·cos(az), cos(el)·sin(az), sin(el))
```

```
        el=90°  ← 바로 위에서 수직 (윗면만 보임)
           │
      el=60°╲
             ╲
        el=30° ╲___  ← 낮은 각도, 측면이 잘 보임
    ─────────────●──────  el=0° = 수평
                물체
```

| 기호 | 의미 |
|---|---|
| **el** (elevation) | 고도각. 0°=수평, 90°=수직 내려다봄 |
| **az** (azimuth) | 방위각. 물체 주위 어느 방향에서 볼지 |
| **standoff** | 축→카메라 거리. 표면이 스윗스팟에 오도록 `WORK_FOCUS(0.25) + 물체반경` |

**왜 el 다양성이 중요한가** — 낮은 el 없이는 옆면·아랫부분이 안 찍히고, 높은 el 없이는
윗면이 안 찍힌다. Spider 는 FOV 가 좁고(~30°) 작동거리가 짧아 한 자세의 커버가 작으므로
더욱 중요하다. 지금 남는 `측면/뒷면 gap` 이 정확히 이 문제다.

az 는 턴테이블이 돌아가므로 커버리지 기여는 작고, 주로 **그 자세에 팔이 닿는지** 찾는 용도.

### ⚠ "도달 불가" 판정이 나오면 — 하드웨어보다 평가기를 먼저 의심하라

**이 절이 이 문서에서 가장 재사용 가치가 높다.** 이번 검토에서 같은 종류의 오류를
세 번 잡았고, 세 번 다 하드웨어가 아니라 평가 코드가 원인이었다. 매번 "레이아웃 한계"로
오인해 **턴테이블 이설까지 검토**했으나 결론은 이설 불필요였다(§4.4).

#### 체크리스트 — 싼 것부터

| # | 의심 | 확인법 | 이번 실측 |
|---|---|---|---|
| 1 | **회전 자유도를 하나로 고정했는가** | roll 을 여러 각도로 시도해 재평가 | el30 `0/8 → 5/8` |
| 2 | **해석 IK 시드가 하나인가** | 시드를 늘려 재평가 | 수직파지 `0/8 → 8/8` |
| 3 | **충돌이 캡슐 근사인가** | 실제 메시 최소거리와 대조 | 캡슐 58mm vs 메시 93mm |
| 4 | **IK "수렴"을 검증했는가** | FK 로 되짚어 위치오차를 찍기 | 0.16~0.39mm (양호) |

#### 왜 1 이 가장 크고 놓치기 쉬운가

`look_at(eye, target, up=(0,0,1))` 은 **자유 DOF 인 roll 을 임의로 하나로 묶는다.**
그런데 이 작업에서 roll 은 실제로 자유롭다:

- **3D 스캐너** — 광축 둘레로 돌려도 같은 면을 본다
- **3핑거 그리퍼 + 축대칭 대상** — 접근축 둘레가 자유

고정하면 7축 팔의 여유자유도를 못 쓰고 도달 가능한 자세를 버린다.
**시드를 12개로 늘려도 el30 은 여전히 0/8** 이었다 — 즉 2 로는 1 을 대체할 수 없다.
증상이 "특정 elevation 대역만 통째로 실패" 라면 1 을 의심하라(시드 문제는 보통
대역 전체가 아니라 산발적으로 실패한다).

#### 대조군을 만들어 원인을 분리하라

세 원인을 한꺼번에 풀면 무엇이 효과였는지 모른다. `--rolls 0` 처럼 **한 요인만 끄는
스위치**를 평가기에 두고 A/B 로 확인할 것.

```bash
scripts/sim/eval_turntable_layout.py --diag 0.365 --rolls 0   # 대조군(roll 고정)
scripts/sim/eval_turntable_layout.py --diag 0.365             # roll 자유
```

#### 그리고 파이프라인 코드에도 같은 제약이 있는지 확인하라

평가기만 고치면 반쪽이다. 이번에도 `isaac_scan_session._view_q` 가 정확히 같은
제약(roll 고정 + 시드 1개)을 갖고 있었고, 그게 Phase1 이 legacy fallback 으로
떨어지던 진짜 원인이었다.

## 4. 실험 결과

### 4.1 el 도달성 — v3 는 낮은 고도각이 전부 막힘

턴테이블 축을 (el, standoff) 에서 보는 자세의 IK 도달성 (az 8방향):

```
el ≤ 30°   전 방위·전 거리 **도달 불가**        ← preview(25°)·Phase1 legacy(30°) 가 여기
el = 40°   거리에 따라 부분 도달
el ≥ 50°   전 방위 도달 (standoff 0.25~0.45)
```

**영향** — `isaac_scan_session` 의 `VIEW_EL_DEG=30`, preview `el=25` 가 모두 실패해
`P1 preview 점 부족(0) → 플래너 불가 → legacy fallback → 자세 IK 전부 실패` 로 이어졌다.
el 을 50 으로 올리고 플래너 후보 `P1_ELS=(50,60,70)` 를 넘겨서 해결(→ 3밴드 스캔 동작).

### 4.2 턴테이블 X 스윕 — 캡슐 기반 초기 결과 (**폐기**)

```
X(m)     점수   통과   el30 el40 el50 el60 el70 el80
-0.20    29.8   27      1    4    5    5    5    7     ★ '최적'
 0.365    1.2    3      0    0    0    0    0    3     ← 현재 v3 ('최악')
```

이 표로 "현재 위치가 최악, X=−0.20 이 최적" 이라 결론지었으나 **전부 캡슐 오탐**이었다.
메시 판정으로 다시 재면 같은 X=0.365 에서 스캔 자세 **29개**가 통과한다(3개가 아니라).

### 4.2b 메시 판정 + 다중 시드 (base Z=1.500)

파지 칸은 접근각 90/75/60/45 별 통과 az 수.

```
X(m)   스캔  파지   el 30/40/50/60/70/80    파지 90/75/60/45
-0.35   13    7    OOOOOO (6종)             0/1/3/3
-0.20   16   26    OOOOOO (6종)             8/8/5/5   ← v4
-0.10   20   31    OOOOOO (6종)             8/8/8/7
-0.05   21   32    OOOOOO (6종)             8/8/8/8   ← 파지 포화 시작
 0.05   26   32    OOOOOO (6종)             8/8/8/8
```

**파지는 X ≥ −0.05 에서 포화(32/32)** 라 변별력을 잃는다 → 판단은 **스캔 자세 수**로 넘어간다.
스캔은 시드를 늘려도 거의 안 변했다(13/14/15… 동일) → 진짜 도달 한계다.
roll 자유도까지 푼 최종 결과는 아래 §4.4.

> 스캔 자세 수의 해석 — 턴테이블이 az 를 채우므로 **el 대역마다 1자세면 성립**한다.
> 자세 수가 많다는 것은 커버리지가 아니라 **계획 여유**(장애물·오차 대응)를 뜻한다.

### 4.3 X=−0.20 으로 옮긴 씬(v4)에서 파이프라인 통과

```
                v3 (축 X=0.365)        v4 (축 X=−0.20)
Phase 1         3밴드 15,019점          3밴드 15,359점
Phase 2 NBV     feasible 없음 → 중단     동작 (+23,485점)
최종 누적        15,019점                38,844점
```

`v4_scene.usd` = `build_scene_v3.py --out v4_scene.usd --turntable-dx -0.565`

단 이 비교는 **v3 쪽이 캡슐 오탐으로 불리하게 나온 상태**였다. 메시 판정으로는 v3 위치도
스캔 자세 29개가 통과하므로, Phase 2 가 막혔던 원인은 "자세가 없다"가 아니라
**el 30·40 이 없어 측면 gap 이 안 줄었다**는 쪽으로 해석해야 한다.

### 4.3b 프레임 20cm 상승 — **높인 쪽이 낫다 (유지)**

세 번의 독립 실행에서 부호가 일관됐다(전체 X 구간 합계):

```
                      스캔        피킹
base Z 1.500 (v3)     399~422    258
base Z 1.407 (v2)     362~391    223~226
                      +8~10%     +14~16%
```

최적점에서의 차이가 더 크다 — base 1.500 은 최적 X 에서 피킹 22, base 1.407 은 13.
팔이 천장에 매달린 구조라 **높을수록 아래쪽 작업공간이 넓어지는** 것이 그대로 나타난다.

### 4.4 결론 — **턴테이블을 옮길 필요가 없다**

roll 자유도까지 풀고 **현재 v3 위치(X=0.365)** 를 재평가한 결과:

```
el=30  5/8      파지 el=90(수직)  8/8
el=40  7/8      파지 el=75        8/8
el=50  7/8      파지 el=60        8/8
el=60  8/8      파지 el=45        8/8
el=70  8/8
el=80  7/8      스캔 IK 실패 0건 (남은 6건은 자가충돌 2 · 환경 4)

IK 위치오차   최대 0.39mm  평균 0.16mm
표면까지 거리  25.0cm (스윗스팟 20~30cm 중앙)
```

요구 3가지가 **현재 위치에서 모두 성립**한다. 파이프라인 실측으로도 확인:

```
                    이설 전(v3)   턴테이블 이설(v4)   roll 수정 후(v3 그대로)
preview                 0점            —                  5,502점
Phase1 자세          el 50~70          —                  el 30
누적 점군            15,019점       38,844점              50,839점
```

**하드웨어를 옮긴 v4(38,844점)보다 옮기지 않고 코드를 고친 쪽(50,839점)이 낫다.**

#### roll 의 기여도 분리 (X=0.365 고정)

| 조건 | el 30 | el 40 |
|---|---|---|
| roll 고정 + 시드 1개 | 0/8 | 0/8 |
| roll 고정 + 시드 12개 | 0/8 | 0/8 |
| **roll 자유** + 시드 12개 | **5/8** | **7/8** |

시드는 **파지에만** 기여했다. 스캔의 낮은 고도각은 오직 roll 로 열린다.
재현: `eval_turntable_layout.py --diag 0.365 --rolls 0` (대조군) vs `--diag 0.365`.

#### roll 을 풀어도 되는가 — 실물 tracking 관점

실물은 스캐너 자체 tracking 에 의존한다(`prompt_on_tracking_lost`,
`nbv_use_relocalization`, `_ROT_RETRY`). 그럼에도 roll 허용이 타당한 근거:

- **패스 내부는 roll 이 상수** — 로봇은 q 를 유지하고 턴테이블만 돈다. 프레임 간 무관.
- **패스 사이는 어차피 위치·자세가 모두 바뀐다** — roll 은 그 점프의 한 성분이고,
  relocalization 이 이미 이를 처리하도록 설계돼 있다.

안전장치: `VIEW_ROLLS_DEG` 는 **크기 순(0,∓45,∓90,180)** 이라 roll=0 해가 있으면 그대로
쓰고, 없을 때만 최소 각도로 넓힌다. 실물에서 tracking-lost 가 늘면
`MMS_SIM_VIEW_ROLLS=0` 으로 즉시 되돌린다.

부수효과: FOV 가 비등방(`SensorModel` hfov 30° / vfov 22.62°)이라 roll 은 0.25m 에서
발자국을 **134×100mm ↔ 100×134mm** 로 회전시킨다. 유효성이 아니라 커버리지 형태 문제.

## 5. ⚠ 충돌 모델 — 캡슐 근사가 오탐을 낸다

**§4.2 의 점수는 이 오탐이 섞인 값이다.** 재평가가 필요하다.

`utils/collision/robot_collision` 의 캡슐 판정과 USD 실제 메시 거리를 대조한 결과:

```
 el  az    캡슐판정      실제 메시 최소거리
 50   0   self:link4     link6:28mm  link5:38  link3:42   (link4 는 42mm 이상)
 60   0   self:link4     link6:28mm  link5:67  link2:93   (link4 는 93mm 이상)
```

캡슐은 "자가충돌"이라는데 **실제로는 42~93mm 여유**가 있다. 원인 두 가지:

**① 링크 캡슐이 관절원점을 잇는 직선** — 꺾인 link4(길이 351mm, r=50mm)를 잘못 덮어,
툴↔link4 축간거리가 58mm 로 계산된다(실제 메시는 93mm 이상).

**② 툴 캡슐이 균일 반경** — 플랜지~카메라를 r=95mm 로 덮는다. §2 프로파일상 플랜지 쪽은
실제 57mm 라 **38mm 과대**(실측 link5 여유가 정확히 38mm). 동시에 265mm 까지 뻗는 Spider
본체를 174mm 에서 잘라 **끝단은 과소**.

②는 `TOOL_SEGMENTS_V3 = ((0, 0.065, 0.057), (0.065, 0.265, 0.106))` 분할 캡슐을 추가해
보정했으나, ①이 남아 오탐이 지속된다.

> 해석 FK 자체는 문제가 아니다 — USD 링크 프레임과 **위치 1.5~8.6mm / 회전 1.4°** 로 일치.
> (`capsules_from_joints` docstring 의 "sim 은 실제 링크 포즈를 써라" 경고는 이 오차가
>  아니라 캡슐 형상 근사 때문에 유효하다.)

**대응** — `eval_turntable_layout.py` 는 캡슐 대신 **USD 실제 메시 최소거리**로 판정한다.
FK 프레임이 정확하므로 로봇을 구동하지 않고 링크 로컬 메시를 FK 로 배치해 빠르게 계산.

## 7. 스캔 전략 — 턴테이블과 로봇의 역할 분담 (2026-08-19)

### 7.1 원칙: 턴테이블 = 방위각, 로봇 = 고도각·거리

§1 에 "az 는 턴테이블이 돌아가므로 커버리지 기여가 작다"고 적었는데, 코드는 반대로
**로봇을 az 8방향으로 돌리고** 있었다(`VIEW_AZIS_DEG = [0,±30,±60,±90,180]`).

실측 대가(물체중심 겨냥, standoff 0.313m):

| az | 관절이동 | 자가여유 | 판정 |
|---|---|---|---|
| **0°** | **58°** | **52mm** | OK |
| −30° | 362° | 12mm | 충돌 |
| −60° | 409° | **3mm** | 충돌 |
| −90° | 445° | **1mm** | 충돌 |

az 를 벌릴수록 팔이 물체를 크게 감싸 이동량 8배·여유 1mm 까지 떨어지고, 16개 중 9개가
충돌로 기각된다. **턴테이블이 공짜로 해줄 일을 로봇이 위험하게 하고 있었다.**

→ `VIEW_AZIS_DEG = [0, 30, -30]` 로 축소. 방위 커버리지는 전회전에 맡긴다.
자세한 표는 `docs/4_collision.md` §7.6.

### 7.2 오목 물체 내부 — 물리적으로 100% 가능하다

컵(지름 126mm, 깊이 77mm) 내부가 스캔 가능한지 두 단계로 확인했다.

**① 센서 기하만** (Spider 작동거리 0.2~0.3m, FOV 30°, 입사각 ≤70°, 테두리 가림 고려)

```
카메라 후보 3,240개 (입구 위)
  내벽      1728/1728 (100%)
  내부바닥   864/864  (100%)
```

**② 로봇 + 턴테이블 전회전까지** — 실제 파이프라인 모델(로봇 한 자세 고정 + 전회전)

```
도달·충돌 통과 자세 280개
최적 1자세: 내벽 100%, 내부바닥 100%
           el=55°, az=0°, standoff 0.25m, 겨냥 z = 물체 중간높이
```

**단 한 자세 + 전회전으로 내부 전체가 덮인다.** 프론티어 자세도, 볼륨 NBV 도 필요 없다.

> ⚠ 처음에 "로봇을 점마다 옮기고 턴테이블 고정" 으로 모델링해 내부바닥 41.7% 라는
> 잘못된 결론을 냈다. **실제 파이프라인과 반대**였다. 회전대칭 물체에서 전회전의
> 이점을 통째로 무시하면 이런 오답이 나온다.

### 7.3 그런데 왜 내부가 안 찍혔나 — gap 검출의 닭·달걀

내부가 물리적으로 가능한데도 NBV 가 그쪽으로 안 간 이유:

**미관측 내벽은 메시에 아예 없고, 없는 면은 경계(gap)로도 잡히지 않는다.**
`detect_gaps` 는 기존 표면의 **경계 루프**를 찾으므로, 미관측 영역 자체를 가리키지 못한다.
그래서 `el_need`(gap 법선에서 계산)가 올라갈 근거가 없고 NBV 는 계속 el 35~45° 만 골랐다.

→ 사전지식으로 보완: `ENSURE_ELS`(기본 55°) 를 gap 과 무관하게 **최소 한 번** 시도한다
(`MMS_SIM_ENSURE_ELS`). 근본 해결은 **볼륨 기반 NBV**(복셀 관측됨/비어있음/미지)지만,
위 실측대로 한 자세면 덮이므로 우선순위는 낮다.

## 8. Phase 3 (바닥면 flip) — watertight 의 필수 조건

**뒤집지 않으면 아랫면은 원리적으로 얻을 수 없다.** boundary 같은 대리 지표로
"이득이 나쁘다"고 저울질할 사안이 아니다(그렇게 판단했다가 정정함).

sim 은 물체가 USD prim 이라 프로그램으로 뒤집는다. 구현하며 걸린 함정 넷:

| # | 증상 | 원인 | 해결 |
|---|---|---|---|
| 1 | flip 이 지워짐 | 턴테이블이 rider `base` 캐시로 매 회전 덮어씀 | `set_rider_flip()` 로 base 에 합성 |
| 2 | 물체가 원판 24mm 관통 | 중심 기준 회전만 시킴 | 회전 후 **원판 위에 앉히기**(원본 AABB+명목회전으로 계산 → 실물도 아는 값) |
| 3 | 2차 flip 크롭 오류 | 1차가 덮어쓴 치수를 원본으로 오인 | `_obj0` 에 원본 고정(flip 각은 **절대각**) |
| 4 | 원판 점 대량 혼입 | 크롭 하한 = 원판 높이 | `DISC_REJECT_M`(3mm) 로 원판 평면 배제 |

**보정은 명목 회전(hint)만 쓴다** — 실물은 사람이 손으로 뒤집으므로 USD 에서 실제 자세를
읽으면 sim 만 정확해져 검증 전제가 깨진다.

### 전역 정합은 이 형상에서 실패한다

flip 정합에 FGR·FPFH+RANSAC 을 시험한 결과(`utils/nbv/global_registration.py`):

```
부분 관측  중첩 20~49%  →  ΔR 144~170°  실패 (fitness 는 0.98 로 높음!)
전체 스윕  중첩 84~86%  →  ΔR 0.0°      성공
```

**fitness 는 게이트가 못 된다** — 회전대칭 표면은 어긋난 각도로도 잘 겹친다(face-merging).
→ `register_consensus`: **방법 간 합의 + AABB 형상 일치**로 판정. 실측에서 fitness 게이트가
통과시킨 오답을 전부 기각했다.

실제 파이프라인에서는 두 방법이 ΔR 103~165° 로 엇갈려 **기각 → hint 폴백**으로 동작 중이다.
실물(사람 손 ±10°)에서 신뢰하려면 **색/텍스처 기반 정합**이 필요하다 — sim 스캐너가
RGBA 를 뽑고도 grayscale 로 버리고 있다(`isaac_scanner.py:73`).

### 국소 ICP 도 같은 형상에서 죽는다 — 그리고 좌표계 함정 (2026-08-19)

flip 후 master 국소 정합의 fitness 0.000 을 추적한 결과, 원인이 셋 겹쳐 있었다:

1. **point-to-plane 은 월드 좌표에서 발산한다.** 원점 기준 미소회전으로 선형화하므로
   점군이 원점에서 멀면(로봇 base 기준 ~0.8m) 회전·이동이 결합한다. 실측: identity
   초기에서 대응점 85.9% 인데 ICP 가 2.9m 폭주 → fitness 0. target 중심으로 평행이동만
   해도 0.981 로 수렴한다.
2. **그런데 중심정렬을 넣으면 결과가 나빠진다**(컵 458→583mm). 발산이 사라지자 ICP 가
   회전대칭축 둘레 108° 회전(기하학적으로 완벽, 실제로는 오답)을 통과시킨다 —
   망가진 ICP 가 우연히 결과를 지켜주고 있었다. → **되돌림**. 대칭 축퇴를 먼저 풀지
   않으면 수치 수정이 독이 된다.
3. **drift 게이트 지표도 월드 좌표에서 무의미하다.** 제자리 회전이 4×4 이동열을
   1272mm 로 부풀린다(점의 실제 이동 69mm). drift 는 이동열이 아니라 실제 점 변위로
   재야 한다(미수정).

한편 **90° 눕힘 자세에서는 국소 ICP 가 성공한다**(Δt 3.4mm, fitness 1.00) — 눕히면
실루엣이 비대칭이라 축퇴가 없다. 색 정합 전까지의 실용 우회로.

### 정합 게이트는 회전만 보고 있었다 — 팽창 검사 (2026-08-19)

기존 게이트 세 겹이 모두 **회전 오류에만** 민감했다:

| 게이트 | 잡는 것 | 놓치는 것 |
|---|---|---|
| 방법 간 합의(FGR vs FPFH) | 한쪽만 틀린 경우 | **둘이 같은 오답에 합의**(대칭 형상) |
| bbox 크기 비교 | 회전 오류 | **평행이동**(크기 안 변함) |
| drift(Δt/Δr) | 큰 보정 | 큰 보정이 옳은 경우와 구분 못 함 |

→ `icp_strategy.union_inflation_m`: 정합 후 **합집합 bbox 가 기준보다 얼마나 커지는가**.
같은 물체이므로 올바른 정합이면 0 에 가깝다(새로 붙는 면은 이미 본 실루엣 *안쪽*을 채운다).
9종 실측에서 분리가 깨끗했다 — 정상 −0.1~3.8mm / 회귀 8.5·10.0mm. 한계 5mm.

효과: laundry 45.1→58.5%, protein_drink 56.5→68.9%, mustard 83.1→93.5% (F@1mm),
**오탐 0건**(정상 7종 정합은 그대로 통과). 전체 평균 75.7→80.2%.

⚠ real 은 게이트가 **아예 없었다** — `_hint_icp_refine` 결과를 무조건 적용하고 fitness·rmse 는
로그만 남겼다. 같은 팽창 게이트를 넣었다(`MMS_REAL_INFLATION_GATE=0` 로 끌 수 있음, 실기 검증 전).

## 8.5 flip 관측 고도각 — 새로 드러난 면에서 정한다

뒤집으면 **어느 면이 새로 보이는지**가 달라지므로 관측 고도각도 달라야 한다.
원래 바닥면 법선 −ẑ 를 flip 회전 R 로 돌린 n_new 를 정면으로 보는 el 을 쓴다:

| flip | n_new | el 목표 | 근거 |
|---|---|---|---|
| 180° | +ẑ | **70°** (내려봄) | 바닥이 위를 향한다 |
| 90°  | 수평 | **30°** (옆면) | 끝면이 옆을 향한다 |

측면뷰 30° 를 고정으로 쓰면 180° flip 후 바닥 입사각이 **60°** 가 되어 입사각
필터(`MAX_INCIDENCE_DEG`=50°)에 **전량 걸린다**. 실측(mug): 굽 링(법선 수평)만
남고 오목한 바닥 중앙이 100% 소실 → completeness 60.8→53.2%. 고도각을 법선에서
산출한 뒤 바닥 중앙 미취득 100%→0%, 입사각 통과 50→68%.

도달·충돌로 걸러 첫 성공을 쓰고 ±15°·기존 30° 를 폴백으로 둔다
(`FLIP_EL_MIN`/`FLIP_EL_MAX` = 30/70°, 고앙각은 자가충돌).

### ⚠ 후보 사다리를 예측·실행이 공유해야 한다 (2026-08-20)

고도각 판정을 넣고도 실행부가 `el_face ± 15°` 를 쓰는 바람에 90·75·105° 가 전부
70° 로 클램프·중복제거되어 **후보가 `[70°, 30°]` 둘뿐**이었다. 70° 실패 시 곧장
30° 로 추락해 바닥이 grazing 이 됐다 — **60° 는 시도조차 안 했는데 실제로는 거의
모든 물체에서 60° 가 도달 가능**했다.

증상이 고약했다: 판정은 "el 60° 도달 가능 — 180° 만" 이라 찍고 실행은 el 30° 로
갔다. 두 경로가 **다른 후보 목록**을 쓴 탓이다.
→ `_flip_view_els(ang)` 하나로 통일(법선에서 시작해 10° 씩 필요 최소치까지 하강,
마지막에 `VIEW_EL_DEG` 폴백). 예측·실행이 같은 함수를 쓰므로 어긋날 수 없다.

실측 효과: 최저 F@1mm 57.7→64.4%, 평균 Chamfer 0.92→0.77mm,
9종 **전부 예측 el = 실행 el**.

## 8.6 90° 눕히기 — 도달 한계는 실재하지 않았다 (재해석)

90° flip 은 "키 큰 물체는 180° 뒤집어도 바닥면을 내려다볼 수 없다"는 도달
한계를 우회하려 도입했다. **그런데 §8.5 의 사다리를 고치자 그 한계가 사라졌다** —
293mm 짜리 세제까지 el 60° 로 바닥을 본다. 한계로 보이던 것은 후보 목록이 60° 를
건너뛴 탓이었고, 판정을 종횡비가 아니라 **실제 도달성**으로 바꾼 덕에 드러났다.

| 물체 | flip 후 꼭대기 z | 채택 el |
|---|---|---|
| laundry (293mm) | 958mm | **60°** |
| spray_can (207mm) | 872mm | **60°** |
| hand_drill (187mm) | 852mm | **60°** |
| mug (77mm) | 742mm | **70°** |

→ 9종 모두 180° 하나로 충분했다. **90° 는 정말 도달 불가한 형상의 안전판**으로
남긴다(도달성 판정이 거짓일 때만 발동). 부수 효과로 눕힌 자세는 실루엣이 비대칭이라
회전대칭체에서 죽던 flip 정합이 살아나므로, 그 용도로도 가치가 있다.

⚠ 이전 판(§8.6 구본)은 "키 큰 물체의 원리적 한계"라고 단정했는데 **틀렸다.**
측정으로 반증된 사례로 남긴다 — 대리 지표(종횡비·키)로 원인을 단정하기 전에
실제 도달성을 풀어 볼 것.

### 종횡비는 **스캔 점군**에서 잰다 (`flip_policy.dims_from_points`)

USD AABB(정답)를 쓰면 실물이 못 하는 판단을 sim 만 하게 되어 검증 전제가 깨진다.
sim 은 누적 점군(`self.accum`), real 은 master 메시 정점으로 **같은 함수**를 부른다.
실측 일치: 스캔 측정 h=208·d=68mm vs 실제 207·68mm.

지름은 **축 둘레 반경의 98 분위수 ×2** 로 잰다 — AABB 폭은 손잡이 때문에 부풀어
종횡비를 낮춘다(mug: AABB 126mm 대 본체 ~96mm).

⚠ flip **배치** 계산(회전 후 원판 안착)은 아직 `_obj0` 의 USD AABB 를 쓴다.
물리 제약에서 나오는 값이라 실물도 스캔 bbox 로 같은 계산이 가능하다 — 미이관.

### 정책·순서 요약

**종횡비 ≥ 2 → 90°(눕히기) → 180°** 순. 90° 가 먼저인 이유: 눕힘 자세에서 정합이
성공하므로 master 를 먼저 넓혀 두면 마지막 180° 의 hint 오차를 흡수하기 쉽다.

**flip 마다 관측자세를 다시 계획한다.** home 자세 캡처는 가용 z 대역(0.67~0.74m)에
물체가 들어오는 낮은 물체에서만 우연히 성립했다 — 다시 세운 207mm 물체는 553점만
잡혔고, 뒤집힌 물체의 새 중심·반경으로 자세를 계획하니 315,850점.
(**Phase 3 = "뒤집힌 물체의 Phase 1"**.)

real 은 같은 정책으로 **사람에게 안내**한다 — `next_flip` 프롬프트가
"옆으로 눕혀 주세요 (90° — 긴 축이 수평이 되게)" 를 출력한다.
