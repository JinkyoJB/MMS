## 0. 결정 요약

이 단계가 내리는 판단 전부와, **무엇을 보고 정하는지**다. 숫자의 근거는 각 절에 있다.

| 무엇을 정하나 | 판정식 / 목적 | 임계 | 코드 |
|---|---|---|---|
| **거리 격자·탐색 한계·시작 거리** | 작동거리 창에서 **유도**한다. 축거리 `d` 에서 창에 드는 반경은 `r ∈ [d−far, d−near]` → 한 스텝이 잡는 반경 폭 = 창 폭 | `r_max` 180mm | `standoff.preview_grid` / `probe_bounds` |
| **다음 축거리** (점이 들어올 때) | 표면거리 **중앙값** `p` 를 창 중앙 `c` 로: `d ← d + (c − p)`. 최댓값이 아니라 중앙값 — 꼬리에 안 흔들린다 | 창 중앙에서 **창폭/4** (최소 10mm) 안이면 유지 | `standoff.distance_correction` |
| **다음 축거리** (점이 0일 때) | **방향을 모른다** → 가까이·멀리 번갈아 탐침. 한쪽이 범위를 벗어나면 살아 있는 쪽으로 계속 | 40mm 씩, 최대 6회 | `standoff.blind_probe` |
| **이 캡처가 유효한가** | 두 단계 **모두** 넘어야 한다 (①이 스캐너 문제, ②가 조준 문제) | ① raw ≥ 1500 (크롭 전) ② 크롭 후 ≥ 200 | `RAW_MIN_VERTS` / `MIN_USEFUL_PTS` |
| **조준높이를 더 올릴까** | 새 캡처가 **물체 상단을 더 늘렸는가**. GT 없이 끝낼 수 있는 유일한 조건 | 증가 < 10mm 면 종료, 최대 4회 | `top_eps_m` / `max_heights` |
| **계획을 낼 수 있나** | 누적 점 수 | ≥ 100 | `MIN_PLAN_PTS` |

**최적화가 아니다.** 여기엔 목적함수가 없고 **되먹임 한 줄**뿐이다 — 한 장 찍고 재서
다음 거리를 계산한다. 탐색이 아니라 **측정**이라 보통 1~2회에 수렴한다.

> **sim 전용 도구다.** 실물은 SDK 가 작동거리 창을 직접 알려주므로

> `MMS_SIM_WD_FILTER=0` 으로 돌려야 한다 — 기본값이면 창 밖 점을 미리 잘라서
> 주므로 넣은 값이 그대로 나오는 순환논법이다.

## 2. 무엇을 어떻게 재는가

| 축 | 어떻게 정하나 |
|---|---|
| 조준높이 `tz` | 원판 상면 **+5cm 에서 시작해 올린다.** "새 캡처가 상단을 더 못 늘리면 종료" — 물체 높이를 모르는 채로 끝낼 수 있다(최대 4회) |
| 축거리 `d` | ★ **들어온 점군의 거리 분포로 조절한다**(§3) |
| 방위 `θ` | 턴테이블 **0/90/180/270° 네 방향**. 각 점군은 `−θ` 로 되돌려 물체 프레임으로 통일. ⚠ 두 방향(0/90°)이면 넓은 물체의 아랫부분은 **반쪽만** 잡혀 플래너가 안 본 쪽을 "면이 없다" 로 오독한다(세제 실측 2026-09-18: 아랫밴드 전부 기각, 커버 58%→94%) |
| 유효 판정 | `min_pts`(기본 200) **미만이면 "안 들어온 것"으로 친다.** 근접한계 안쪽에서도 노이즈 몇 점은 나오는데, 그걸 "들어왔다"로 보면 중앙값이 엉뚱해져 거리가 **틀린 방향으로** 수렴한다 |

`d` 는 **턴테이블 축까지의 거리**다. 작동거리 창은 **표면까지의 거리**로 정의되므로
둘을 섞으면 안 된다 — 반경 97mm 물체에서 축거리 225mm 는 표면 128mm 로, Spider
근접한계(170mm) 안쪽이라 데이터가 아예 안 나온다. 변환은 `standoff.axis_standoff(r)`
한 곳에서만 한다.

## 3. 거리를 정하는 법

### 먼저 — 거리는 전부 **작동거리 창에서 유도**된다

하드코딩된 거리가 없다. 격자·탐색한계·시작거리가 모두 `dof`(스캐너가 알려주는
near/far)에서 계산된다(`standoff.preview_grid` / `probe_bounds` /
`preview_start_distance`).

근거는 기하 하나다. 카메라는 **축**을 거리 `d` 에서 겨누는데 스캔되는 건 **표면**이다:

```
   카메라 ●──────────── d ────────────┆ 축
              ├── d−r ──┤
                        ○ 표면 (축에서 반경 r)
```

표면까지가 `d − r` 이므로, 창 안에 드는 반경은

```
near ≤ d − r ≤ far     ⟺     r ∈ [d − far,  d − near]
```

**한 거리가 잡는 것은 반경 한 구간이고, 그 폭이 곧 창 폭(far − near)이다.** 그래서
반경 0~`r_max` 를 덮으려면 창 폭 간격으로 스텝을 놓으면 된다 — `d_k = far + k·(far−near)`.

창 **200~300mm**(폭 100mm) · `r_max` **180mm** 면:

| `d` | 창에 드는 반경 |
|---|---|
| **300mm** | r = 0 ~ 100mm |
| **400mm** | r = 100 ~ 200mm |

두 스텝으로 r 0~200mm 가 이어붙는다. **어느 스텝에 잡히는지 자체가 반경 측정이다.**
탐색 한계도 같은 식이다 — 하한 `near`(r=0), 상한 `far + r_max` → **200~480mm**.

창이 바뀌면 전부 따라온다:

| 창 | 폭 | 격자 | 탐색한계 |
|---|---|---|---|
| 200~300 (현재 가정) | 100mm | (300, 400) | 200~480 |
| **170~350** (Spider 스펙) | 180mm | **(350)** — 한 스텝 | 170~530 |
| 210~265 (좁게 튜닝) | 55mm | (265, 320, 375, 430) | 210~445 |

> ⚠ 2026-09-17 이전에는 이 값이 **양쪽에 하드코딩돼 갈라져 있었다.**
> sim `(300, 380)` / real `(240, 300)`. real 쪽 240mm 는 창 200~300 기준으로
> `r ∈ [−60, 40]` 이라 **반경 40mm 만 넘으면 첫 스텝에서 점이 하나도 안 나왔다.**
> 창을 바꾸면(`set_scanning_range`·기종 교체) 둘 다 조용히 틀려진다.

### 점이 들어올 때 — 한 장으로 다음 거리가 나온다

카메라는 축을 거리 `d` 에서 겨눈다. 표면까지 거리 중앙값 `p` 가 나오면 그 방위의
국소 반경이 `r ≈ d − p` 다. 표면을 작동거리 창 **중앙** `c` 에 놓으려면

```
d_next = c + r = d + (c − p)
```

중앙값을 쓰는 이유는 히스토그램 꼬리(바닥·배경 잔재)에 안 흔들리기 때문이다.
창 중앙에서 불감대(창 폭의 1/4) 안이면 움직이지 않는다.

예전엔 위 격자를 **높이마다 전부** 돌았다. 먼 스텝은 작은 물체에서 빈 캡처가 되는데
(sim 실측 380mm 에서 3,233점 ≈ 0) 이동은 매번 했다 — 실물에서 그냥 시간 낭비다.
지금 격자는 **적응이 실패했을 때의 폴백**으로만 남는다(옛 콜백 계약 호환).

수렴한 거리는 `d_cur` 로 **다음 높이·다음 방위에 이월**된다. 그래서 첫 높이만 몇 번
움직이고 이후는 대개 1회다 (실측 10회 이동 → **8회**, 전부 유효).

### 점이 하나도 안 들어올 때 — 양쪽으로 벌린다

**반환 0 은 "방향을 모른다"는 뜻이다.** 가까이·멀리를 번갈아 벌려 가며 찾는다.

```
k=1: d−40mm   k=2: d+40mm   k=3: d−80mm   k=4: d+80mm   …   (최대 6회)
탐색 한계 = [작동거리 near, 작동거리 far + 최대반경] = 200~480mm
```

> ⚠ 2026-09-17 이전에는 **가까이만** 갔다. 근거는 "실물 실패는 너무 멀어서였다" 는
> 관찰이었는데, 그 관찰은 축거리와 표면거리를 구분하기 **전**의 것이다. 반경 110mm
> 짜리 물체면 시작 축거리 300mm 가 표면 190mm — 근접한계 안쪽이라 반환이 0 이고,
> 거기서 더 가까이 가면 **탐색이 실패 방향으로 달려간다.** 실제로 그 경우 못 찾았다.
>
> 가까운 쪽을 **먼저** 보는 순서는 유지한다 — 멀어서 비는 경우가 여전히 더 흔하고,
> 가까운 쪽이 밀도·정밀도에도 유리하다.

검증 — 합성 콜백, 창 200~300mm, 시작 300mm
(`scripts/nbv/verify_preview_contract.py` 와 같은 방식):

| 경우 | 로그 | 이동 |
|---|---|---|
| 보통 r=40mm | `d=300 표면 260mm ≈ 창중앙 — 유지` | **1회** |
| 작은 r=5mm | `d=300 표면 295mm → −45mm (300→255)` · `d=255 표면 250mm — 유지` | **2회** |
| 큰 r=110mm (시작이 근접한계 안쪽) | `d=300 반환0 → 260 탐침` · `d=260 반환0 → 340 탐침` · `d=340 표면 230mm — 유지` | **3회** |

## 4. 계약 — `(점군, 카메라위치)` 2-튜플

콜백이 **카메라 위치를 같이 줘야** 적응이 켜진다(표면거리를 못 재면 보정식이 성립
안 한다). 판정은 **모양**으로만 한다 — 2-튜플인가.

| 콜백 반환 | 해석 |
|---|---|
| `(pts, cam)` | 정상 |
| `(pts, None)` | **이번 프레임만** 카메라를 못 읽음 → 보정만 건너뛰고 **적응 유지** |
| `pts` (맨 배열) | 옛 계약 → 고정 격자로 영구 전환 |

> ⚠ 예전엔 이 둘을 `cam is None` 하나로 겸했다. 그래서 빈 캡처 한 번에 **실행
> 내내 적응이 영구히 꺼졌고**, 그 판정이 탐침보다 **앞**에 있어서 빈 캡처가
> `blind_probe` 에 도달조차 못 했다 — 적응이 가장 필요한 순간에 정확히 꺼지는
> 구조였다. real 쪽은 return 5곳이 전부 맨 배열이라 **적응이 한 번도 안 돌았다.**
>
> 같은 결함이 하루에 네 번 나왔고 전부 **조용히** 나빠졌다(스캔은 끝나고 결과도
> 나오는데 거리만 안 맞는다). 그래서 정적 검사를 상설로 뒀다 — 하드웨어·Isaac
> 없이 0.3초다:
>
> ```bash
> env -u PYTHONPATH python scripts/nbv/verify_preview_contract.py
> ```

## 5. 손잡이

| env | 기본 | 뜻 |
|---|---|---|
| `MMS_WORK_STANDOFF_MM` | 225 | 카메라↔**표면** 목표 거리. **물리값** — 실측 작동거리 창의 중앙에 두고 그대로 둔다 |
| `MMS_STANDOFF_BIAS_MM` | 0 | **오차 주입.** 일부러 틀린 거리에서 출발시켜 추종이 되돌리는지 본다 |
| `MMS_PREVIEW_RADIUS_MAX_MM` | 180 | preview 가 상정하는 **최대 물체 반경.** 거리격자 스텝 수와 탐색 상한을 같이 결정한다(§3). 더 굵은 물체를 다루면 올린다 |
| `MMS_SIM_PREVIEW_EL` | 30 | preview 고도각 (sim) |
| `MMS_SIM_WD` / `MMS_SIM_WD_FILTER` | — | sim 스캐너의 작동거리 창과 필터 on/off |

작동거리 창 자체(near/far)는 **스캐너에게 물어본다** — real 은 SDK `scanning_range()`,
sim 은 그 계약을 모사한다(`IsaacArtecScanner.scanning_range`). 계획기의 가정과
스캐너의 설정이 갈라지지 않게 하려는 것이다. 값을 바꾸려면 `ArtecConfig` 의
`scan_range_near_mm` / `scan_range_far_mm`.

> ⚠ `WORK_STANDOFF_MM` 과 `BAND_OVERLAP`(`3_lookaround.md` §5)은 **같은 증상의 두 해법**
> 이다. 둘 다 당기면 이중보정이다 — 겹침 쪽만 쓴다.

# 〔부록〕 Troubleshooting

### P1. preview 가 점을 하나도 못 모은다
먼저 **어느 쪽으로 끝났는지** 본다. 소진 메시지가 두 가지이고 뜻이 반대다.

```
… 반환 없음, 탐색범위(200~480mm) 소진        ← 가능한 거리를 다 훑었는데도 없다
… 시도 6회 소진 (다음 후보 460mm — 안 감)     ← 볼 거리가 남았는데 예산이 끝났다
```

**`시도 N회 소진`** 이면 거리 문제일 수 있다. 굵은 물체라 시작 거리에서 멀거나
`max_dist_tries`(기본 6)가 모자란 것이다 — 올려서 다시 돌린다.

**`탐색범위 … 소진`** 이면 거리 문제가 **아니다.** 아래를 본다:

- **카메라가 딴 데를 본다** — `output/debug/preview/` 의 스냅샷을 먼저 열어라.
  2026-09-17 에 `crop=0` 을 두고 IK·충돌·프레임 변환·관절 리밋을 차례로 배제하다가
  원인이 **카메라가 딴 데를 보던 것**이었던 적이 있다(USD articulation 영점과 해석 FK
  영점이 29° 어긋나 있었다 — `isaac_xarm.JOINT_ZERO_OFFSET`). 그림 한 장이면 끝난다.
- **크롭이 물체를 통째로 버린다** — `crop_object_points` 의 축·디스크 상면·`up_sign`.
  real 은 base 가 +Z 아래라 `up_sign=-1` 이어야 한다(`docs/collision.md` §6.1).
- **`pts=N — N점뿐 (<200)`** 이 반복되면 스캐너는 뭔가 보는데 그게 물체가 아니다 —
  자기점 잔여·배경이다. 문턱은 `min_pts`(§5).

스냅샷은 `output/debug/preview/<실행시각>_<순번>_preview_tz…_d….png` 로 쌓인다 —
실행마다 지우지 않으므로 직전 실행과 나란히 놓고 비교할 수 있다.

### P2. 물체 높이를 실제보다 작게 잡는다
상단 종료 조건(`top_eps_m`, 기본 1cm)과 최대 높이 횟수(4회)를 본다. 얇은 돌출부는
"상단이 안 늘었다" 로 오판될 수 있다. 밴드 센터 inset 이 이를 일부 보정하지만
(`3_lookaround.md` §5) 근본 대책은 아니다.

실측 2026-09-16: 플래너 `h=215mm` 인데 결과 메시는 **252mm** 였다.

### P3. 탐색이 한쪽 한계에서 멈춘다 (2026-09-17 수정됨)
증상 — 브래킷은 좌우로 번갈아 벌어지는데, **좁은 쪽이 먼저 소진되면 넓은 쪽에 남은
거리를 못 써 봤다.** `blind_probe` 가 `k` 번째 탐침이 `[lo, hi]` 밖이면 `None` 을
돌려줬고, 호출부는 그걸 "다 썼다" 로 읽어 탐색을 통째로 끝냈기 때문이다.

창 200~300 · 시작 300mm · 탐색한계 200~480mm 에서:

```
이전:  260 · 340 · 220 · 380 · (180 = 한계 밖) → 중단
       실효 범위 220~380mm. 상한 480mm 는 이름만 남는다.
지금:  260 · 340 · 220 · 380 · 420 · 460       ← 180 을 건너뛰고 먼 쪽으로 계속
```

범위 밖 탐침은 **건너뛰고** 다음 유효 탐침을 센다. `None` 은 **양쪽 모두** 소진된
경우에만 나오므로, 로그의 "탐색범위 소진" 도 그제서야 사실이 된다.

> 남은 제약은 **예산**이다 — `max_dist_tries=6` 이라 한 조준높이에서 캡처는 6회
> (시작 1 + 탐침 5)까지다. 위 수열이면 420mm 까지 간다. 탐침 하나가 곧 로봇 이동
> 1회라 무한정 늘릴 수는 없다. 구조적으로 잘리던 것과 달리 이건 의도한 상한이고,
> 굵은 물체에서 모자라면 `max_dist_tries` 를 올린다.

### P4. 〔미검증〕 real 에서 양쪽 브래킷·노이즈 문턱을 안 돌려봤다
§3 의 양쪽 탐색과 `min_pts` 문턱은 **sim 합성 콜백으로만** 검증했다
(`scripts/nbv/verify_preview_contract.py`). 실물에서 확인할 것:

- 근접한계 안쪽이 **0 점**이 아니라 **노이즈 몇 점**으로 나올 때 `min_pts`(200)가
  실제로 걸러 주는가. 문턱을 넘는 노이즈가 나오면 중앙값이 엉뚱해져 거리가 이상한
  쪽으로 간다. 로그에 `N점뿐 (<200) — 노이즈로 보고 버림` 이 보이면 잘 걸린 것이다.
- 굵은 물체(r≳100mm)에서 탐침 수열이 **먼 쪽으로 계속 벌어지는가.**
  sim 런은 r=34mm 라 첫 스텝에서 바로 잡혀 이 경로를 한 번도 안 탔다.

`output/debug/preview/` 스냅샷과 같이 볼 것.
